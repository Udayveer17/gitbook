# Payload Encryption Xor & AES

### Why Do We Need Payload Encryption?

Encrypted:- shellcode is employed to evade static detection. Static detection mechanisms search for signatures within the code to identify potential threats. For instance, in shellcode detection mechanisms like sandboxes, static evasion techniques look for null byte combinations within the shellcode to determine whether it is malicious. By encrypting the payload, we can obfuscate these signatures, making it harder for static analysis tools to recognize and flag the code as malicious.

## **Payload Encryption XOR**

### **Why XOR is Used in Malware:**

1. **Reversible**: If `A + B = C`, then `C+⊕ B = A` Same operation encrypts AND decrypts
2. **Fast**: Extremely efficient computation
3. **Simple**: Easy to implement in any language
4. **Effective**: Breaks signature-based detection

### **Incremental XOR Encryption**

```c
for (i = 0; i < shellcode_size; i++) {
    shellcode[i] = shellcode[i] ^ (bKey + i);
}
```

**How it works:** Each byte uses a DIFFERENT key based on its position in the payload. The key for each position is calculated as the base key plus the position index. So byte 0 gets XORed with `bKey + 0`, byte 1 gets XORed with `bKey + 1`, byte 2 gets XORed with `bKey + 2`, and this pattern continues throughout the entire payload.

**Example with bKey = 'u' (117):**

* Byte 0 → XOR with (117 + 0) = 117 → 'u'
* Byte 1 → XOR with (117 + 1) = 118 → 'v'
* Byte 2 → XOR with (117 + 2) = 119 → 'w'
* Byte 3 → XOR with (117 + 3) = 120 → 'x'
* Byte 4 → XOR with (117 + 4) = 121 → 'y'

**Why it's better than static XOR:** Even if an attacker guesses the correct starting key, each byte requires a different key value because of the incrementing pattern. Automated tools that expect static XOR encryption will fail since they assume the same key works for all bytes. This makes brute-force attempts more difficult and time-consuming.

**Limitations:** There are still only 256 possible starting keys to try. The pattern is predictable since it's just adding the position to the base key. A determined analyst who understands the algorithm can still test all 256 possibilities. This technique is considered obfuscation rather than true cryptographic security.

### **Multi-Byte Repeating Key XOR Encryption**

```c
for (size_t i = 0, j = 0; i < sShellcodeSize; i++, j++) {
    if (j >= sKeySize){
        j = 0;
    }
    pShellcode[i] = pShellcode[i] ^ bKey[j];
}
```

**How it works:** Uses a full key consisting of multiple bytes that repeat cyclically across the payload. Two index variables track position: `i` tracks which shellcode byte is being processed, while `j` tracks which key byte is currently being used. Both start at zero and increment together. When `j` reaches the end of the key, it resets back to zero, causing the key to repeat throughout the entire payload.

**Example with key "uday" (4 bytes):**

* Byte 0 → XOR with 'u'
* Byte 1 → XOR with 'd'
* Byte 2 → XOR with 'a'
* Byte 3 → XOR with 'y'
* Byte 4 → XOR with 'u' (key resets and repeats)
* Byte 5 → XOR with 'd'
* Byte 6 → XOR with 'a'
* Byte 7 → XOR with 'y'
* Pattern continues until all bytes are processed

**Security benefits:** Keyspace expands exponentially with key length. A 1-byte key offers only 256 possibilities, but a 4-byte key offers over 4 billion combinations. An 8-byte key offers more than 18 quintillion possibilities. This makes brute-force attacks computationally infeasible for automated tools. Unlike incremental XOR, there is no predictable mathematical relationship between key bytes, making it much harder to crack.

**Important property:** XOR is self-inverse, meaning the same function handles both encryption and decryption. If you pass encrypted data through this function with the same key, it returns the original data because (A XOR B) XOR B = A. This eliminates the need for separate encryption and decryption routines.

**Implementation considerations:** Key length should balance security versus binary size. Use randomly generated bytes instead of ASCII strings to avoid predictability. The key can be hardcoded into the malware, generated at runtime using system entropy, or retrieved from a command and control server.

***

### **Self-Inverse Property of XOR**

**The Magic Property:** XOR is reversible using the same operation. If A XOR B = C, then C XOR B = A. This means encryption and decryption use the exact same code.

**Example:**

```
'H' XOR 'u' = '='   (encryption)
'=' XOR 'u' = 'H'   (decryption - same XOR operation)
```

**Why this matters for malware:**

* No need to write separate encryption and decryption functions
* Reduces code complexity and potential bugs
* Saves space in the malware binary
* Makes implementation simpler and more reliable

### How XOR Works with Hex Shellcode and String Key

At its most basic level, everything in a computer is just bytes - numbers from 0 to 255. Whether you're looking at hex shellcode like `\xfc\x48\x83` or a string like "uday", they're all just sequences of bytes stored in memory. The shellcode `\xfc\x48\x83\xe4\xf0` is stored as bytes with decimal values 252, 72, 131, 228, and 240. The key "uday" is stored as bytes with decimal values 117, 100, 97, and 121. When the XOR function runs, it takes each shellcode byte and XORs it with the corresponding key byte. The XOR operation doesn't care about format - it just sees numbers and performs mathematical operations on them. For the first byte, the shellcode value 252 is XORed with the first key byte 117, which gives 137 (displayed as `\x89` in hex). The second byte takes shellcode value 72 and XORs it with the second key byte 100, resulting in 44 (`\x2c`). The third byte uses 131 XOR 97 to get 226 (`\xe2`). The fourth byte uses 228 XOR 121 to get 173 (`\xad`). When we reach the fifth byte, the key has run out, so it resets back to the first key byte 'u' (117). The shellcode value 240 XOR 117 gives 133 (`\x85`). This pattern continues until every byte of the shellcode is processed.

## **Payload Encryption - AES Encryption**

***

### Primary Reasons for Using AES in Malware

#### 1. Stronger Protection Against Analysis

AES provides **cryptographic-grade security** that cannot be broken through brute-force attacks. With a 256-bit key, there are 2^256 possible combinations, which is astronomically larger than XOR's 256 possibilities. Even with massive computing power, it would take billions of years to brute-force an AES256 key. This makes it practically impossible for security analysts to decrypt the payload without knowing the key.

#### 2. Resisting Automated Analysis Tools

Modern sandboxes and security tools are equipped with heuristics that detect and break simple XOR encryption. These tools can identify patterns like repeated key bytes or predictable incremental patterns in XOR-encrypted data. AES encryption produces ciphertext that is statistically random and shows no discernible patterns, making it extremely difficult for automated tools to recognize that encryption has even been applied, let alone break it.

#### **AES Encryption**

* symmetric-key algorithm meaning the same key is used for both encryption and decryption. There are several types of AES encryption such as AES128, AES192, and AES256 that vary by the key size. For example, AES128 uses a 128-bit key whereas AES256 uses a 256-bit key.
* AES can use different [block cipher modes of operation](https://en.wikipedia.org/wiki/Block_cipher_mode_of_operation) such as CBC, GCM and etc.
* A mode of operation describes how to repeatedly apply a cipher's single-block operation to securely transform amounts of data larger than a block
* Most modes need a unique binary sequence called IV, IV must be non-repeating and for some modes also random. The idea of IV is to make sure distinct cipher texts are produced for same plaintext and key everytime
* If the payload being encrypted is not a multiple of 16 bytes then padding is required to increase the size of the payload and make it a multiple of 16 bytes.
* For both CBC mode and CFB mode, the initialization vector is the size of a block, which for AES is 16 bytes = 128 bits. For [CFB mode](https://en.wikipedia.org/wiki/Block_cipher_mode_of_operation#CFB), the IV must never be reused for different messages under the same key; for [CBC mode](https://en.wikipedia.org/wiki/Block_cipher_mode_of_operation#CBC), the IV must never be reused for different messages under the same key, _and_ must be unpredictable in advance by an attacker. Using successive integers as the IV is fine for CFB but not fine for CBC.

### What is an IV?

An **Initialization Vector (IV)** is a fixed-size random or pseudo-random value that is used alongside the encryption key to start the encryption process. Think of it as a "starting point" or "initial state" that makes each encryption unique, even when encrypting the exact same data with the exact same key.

### Why is it Called a "Binary Sequence"?

An IV is called a "binary sequence" because it's simply a sequence of bytes (0s and 1s) - just like any other data on a computer. In AES, the IV is always **16 bytes (128 bits)**, which is the same size as a single AES block. These 16 bytes are just a random pattern of bits like `10110101 00111010 11110000 ...`

**Example of a 16-byte IV in hex**

```
B4 C8 1D 1D 14 7C CB FA 07 42 D9 ED 1A 86 D9 CD
```

This is just 16 random numbers, but in binary it's 128 bits of random data.

#### **Cryptographic Next Generation**

CNG Provides a set of cryptographic functions that can be used by OS applications. So it provides a standard interface for cryptographic operations, making it easier for developers to implement security features in their applications. Replaces the old CryptoAPI.

The InstallAesEncryption and InstallAesDecryption both make use of CNG:

The BCrypt Library functions used are as follows:

* [BCryptOpenAlgorithmProvider](https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/nf-bcrypt-bcryptopenalgorithmprovider) - Used to load the [BCRYPT\_AES\_ALGORITHM](https://learn.microsoft.com/en-us/windows/win32/seccng/cng-algorithm-identifiers) Cryptographic Next Generation (CNG) provider to enable the use of cryptographic functions.
* [BCryptGetProperty](https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/nf-bcrypt-bcryptgetproperty) - This function is called twice, the first time to retrieve the value of [BCRYPT\_OBJECT\_LENGTH](https://learn.microsoft.com/en-us/windows/win32/seccng/cng-property-identifiers) and the second time to fetch the value of [BCRYPT\_BLOCK\_LENGTH](https://learn.microsoft.com/en-us/windows/win32/seccng/cng-property-identifiers) property identifiers.
* [BCryptSetProperty](https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/nf-bcrypt-bcryptsetproperty) - Used to initialize the `BCRYPT_OBJECT_LENGTH` property identifier.
* [BCryptGenerateSymmetricKey](https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/nf-bcrypt-bcryptgeneratesymmetrickey) - Used to create a key object from the input AES key specified.
* [BCryptEncrypt](https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/nf-bcrypt-bcryptencrypt) - Used to encrypt a specified block of data. This function is called twice, the first time retrieves the size of the encrypted data to allocate a heap buffer of that size. The second call encrypts the data and stores the ciphertext in the allocated heap.
* [BCryptDestroyKey](https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/nf-bcrypt-bcryptdestroykey) - Used to clean up by destroying the key object created using `BCryptGenerateSymmetricKey`.
* [BCryptCloseAlgorithmProvider](https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/nf-bcrypt-bcryptclosealgorithmprovider) - Used to clean up by closing the object handle of the algorithm provider created earlier using `BCryptOpenAlgorithmProvider`.
* [BCryptDecrypt](https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/nf-bcrypt-bcryptdecrypt)
* Used to decrypt a specified block of data. This function is called twice, the first time retrieves the size of the decrypted data to allocate a heap buffer of that size. The second call decrypts the data and stores the plaintext data in the allocated heap.

**Padding**

Both `InstallAesEncryption` and `InstallAesDecryption` functions use the `BCRYPT_BLOCK_PADDING` flag with the `BCryptEncrypt` and `BCryptDecrypt` bcrypt functions respectively, which will automatically pad the input buffer, if required, to be a multiple of 16 bytes, solving the AES padding issue.

BOOL InstallAesEncryption(PAES pAes) {
	/*Passing by reference, because we need to modify the actual struct and not its copy*/

	/*Initialising imp values*/
	BOOL bSTATE = TRUE;
	BCRYPT_ALG_HANDLE hAlgorithm = NULL;
	BCRYPT_KEY_HANDLE hKeyHandle = NULL;

	ULONG cbResult = NULL;
	DWORD dwBlockSize = NULL;

	DWORD cbKeyObject = NULL;
	PBYTE pbKeyObject = NULL;

	PBYTE pbCipherText = NULL;
	DWORD cbCipherText = NULL;

	NTSTATUS STATUS = NULL;

	// Initialising "hAlgorithm" as AES algo handle

	STATUS = BCryptOpenAlgorithmProvider(&hAlgorithm, BCRYPT_AES_ALGORITHM, NULL, 0);
	if (!NT_SUCCESS(STATUS)) {
		printf("[!] BCryptOpenAlgorithmProvider failed with error: 0x%0.8X\n", STATUS);
		bSTATE = FALSE; goto _EndOfFunc;
	}

	//Getting the size of the key object variable pKeyObject. This is used by the BCryptGenerateSymmetricKey 
	//..function later.

	STATUS = BCryptGetProperty(hAlgorithm, BCRYPT_OBJECT_LENGTH, (PBYTE)&cbKeyObject, sizeof(DWORD), &cbResult, 0);
	if (!NT_SUCCESS(STATUS)) {
		printf("[!] BCryptGetProperty[1] failed with Error: 0x%0.8X\n", STATUS);
		bSTATE = FALSE; goto _EndOfFunc;
	}

	//Getting the size of block used in encryption. Since this is AES it must be 16 bytes.
	STATUS = BCryptGetProperty(hAlgorithm, BCRYPT_BLOCK_LENGTH, (PBYTE)&dwBlockSize, sizeof(DWORD), &cbResult, 0);
	if (!NT_SUCCESS(STATUS)) {
		printf("[!] BCryptGetProperty[2] failed with Error: 0x%0.8X\n", STATUS);
		bSTATE = FALSE; goto _EndOfFunc;
	}

	if (dwBlockSize != 16) {
		bSTATE = FALSE; goto _EndOfFunc;
	}

	//Allocating memory for the key object
	pbKeyObject = (PBYTE)HeapAlloc(GetProcessHeap(), 0, cbKeyObject);
	if (pbKeyObject == NULL) {
		bSTATE = FALSE; goto _EndOfFunc;
	}

	//Setting Block Cipher Mode to CBC, uses 32 byte key and 16byte IV
	STATUS = BCryptSetProperty(hAlgorithm, BCRYPT_CHAINING_MODE, (PBYTE)BCRYPT_CHAIN_MODE_CBC, sizeof(BCRYPT_CHAIN_MODE_CBC), 0);
	if (!NT_SUCCESS(STATUS)) {
		printf("[!] BCryptSetProperty Failed with Error: 0x%0.8X \n", STATUS);
		bSTATE = FALSE; goto _EndOfFunc;
	}

	//Generating the key object from the AES key "pAes->pKey". The output will be saved in pKeyObject and will be size cbKeyObject
	STATUS = BCryptGenerateSymmetricKey(hAlgorithm, &hKeyHandle, pbKeyObject, cbKeyObject, (PBYTE)pAes->pKey, KEYSIZE, 0);
	if (!NT_SUCCESS(STATUS)) {
		printf("[!] BCryptGenerateSymmetricKey Failed with Error: 0x%0.8X \n", STATUS);
		bSTATE = FALSE; goto _EndOfFunc;
	}

	//Running BCryptEncrypt first time with NULL output parameters to retrieve the size of the output buffer which is saved in cbCipherText
	STATUS = BCryptEncrypt(hKeyHandle, (PUCHAR)pAes->pPlainText, (ULONG)pAes->dwPlainSize, NULL, pAes->pIv, IVSIZE, NULL, 0, &cbCipherText, BCRYPT_BLOCK_PADDING);
	if (!NT_SUCCESS(STATUS)) {
		printf("[!] BCryptEncrpt[2] Failed with Error: 0x%0.8X\n", STATUS);
		bSTATE = FALSE; goto _EndOfFunc;
	}

	// Allocating enough memory for the output buffer, cbCipherText
	pbCipherText = (PBYTE)HeapAlloc(GetProcessHeap(), 0, cbCipherText);
	if (pbCipherText == NULL) {
		bSTATE = FALSE; goto _EndOfFunc;
	}

	// Running BCryptEncrypt again with pbCipherText as the output buffer
	STATUS = BCryptEncrypt(hKeyHandle, (PUCHAR)pAes->pPlainText, (ULONG)pAes->dwPlainSize, NULL, pAes->pIv, IVSIZE, pbCipherText, cbCipherText, &cbResult, BCRYPT_BLOCK_PADDING);
	if (!NT_SUCCESS(STATUS)) {
		printf("[!] BCryptEncrypt[2] Failed With Error: 0x%0.8X \n", STATUS);
		bSTATE = FALSE; goto _EndOfFunc;
	}

	//Cleanup
_EndOfFunc:
	if (hKeyHandle)
		BCryptDestroyKey(hKeyHandle);
	if (hAlgorithm)
		BCryptCloseAlgorithmProvider(hAlgorithm, 0);
	if (pbKeyObject)
		HeapFree(GetProcessHeap(), 0, pbKeyObject);
	if (pbCipherText != NULL && bSTATE) {
		//If everything worked, save pbCipherText and cbCipherText
		pAes->pCipherText = pbCipherText;
		pAes->dwCipherSize = cbCipherText;
	}
	return bSTATE;
}

	NTSTATUS STATUS = 0; // FIXED: NULL -> 0

	//Initialising the "hAlgorithm" as AES algorithm handle
	STATUS = BCryptOpenAlgorithmProvider(&hAlgorithm, BCRYPT_AES_ALGORITHM, NULL, 0);
	if (!NT_SUCCESS(STATUS)) {
		printf("[!] BCryptOpenAlgorithmProvided Failed with Error: 0x%0.8X\n", STATUS);
		bSTATE = FALSE; goto _EndOfFunc;
	}

	// Getting the size of the key object variable pbKeyObject. This is used by the BCryptGenerateSymmetricKey function later
	STATUS = BCryptGetProperty(hAlgorithm, BCRYPT_OBJECT_LENGTH, (PBYTE)&cbKeyObject, sizeof(DWORD), &cbResult, 0);
	if (!NT_SUCCESS(STATUS)) {
		printf("[!] BCryptGetProperty[1] Failed With Error: 0x%0.8X \n", STATUS);
		bSTATE = FALSE; goto _EndOfFunc;
	}

	//Getting the size of the block used in encryption. since its AES it should be 16 bytes
	STATUS = BCryptGetProperty(hAlgorithm, BCRYPT_BLOCK_LENGTH, (PBYTE)&dwBlockSize, sizeof(DWORD), &cbResult, 0);
	if (!NT_SUCCESS(STATUS)) {
		printf("[!] BCryptGetProperty Failed with Error: 0x%0.8X\n", STATUS);
		bSTATE = FALSE; goto _EndOfFunc;
	}

	//Checking if Block Size is 16 bytes
	if (dwBlockSize != 16) {
		bSTATE = FALSE; goto _EndOfFunc;
	}

	// Allocating Memory for the key object
	pbKeyObject = (PBYTE)HeapAlloc(GetProcessHeap(), 0, cbKeyObject);
	if (pbKeyObject == NULL) {
		bSTATE = FALSE; goto _EndOfFunc;
	}

	//Setting block cipher mode to CBC. 
	STATUS = BCryptSetProperty(hAlgorithm, BCRYPT_CHAINING_MODE, (PBYTE)BCRYPT_CHAIN_MODE_CBC, sizeof(BCRYPT_CHAIN_MODE_CBC), 0);
	if (!NT_SUCCESS(STATUS)) {
		printf("[!] BCryptSetProperty Failed With Error: 0x%0.8X\n", STATUS);
		bSTATE = FALSE; goto _EndOfFunc;
	}

	// Generating the key object from the AES key "pAes->pKey". The output will be saved in pbKeyObject of size cbKeyObject
	STATUS = BCryptGenerateSymmetricKey(hAlgorithm, &hKeyHandle, pbKeyObject, cbKeyObject, pAes->pKey, KEYSIZE, 0);
	if (!NT_SUCCESS(STATUS)) {
		printf("[!] BCryptGenerateSymmetricKey Failed with Error: 0x%0.8X\n", STATUS);
		bSTATE = FALSE; goto _EndOfFunc;
	}

	//Running BCryptDecrypt first time with NULL output parameters to retrieve the size of the output buffer which is saved in plain text
	STATUS = BCryptDecrypt(hKeyHandle, (PUCHAR)pAes->pCipherText, (ULONG)pAes->dwCipherSize, NULL, pAes->pIv, IVSIZE, NULL, 0, &cbPlainText, BCRYPT_BLOCK_PADDING);
	if (!NT_SUCCESS(STATUS)) {
		printf("[!] BCryptDecrypt[1] Failed with Error: 0x%0.8X\n", STATUS);
		bSTATE = FALSE; goto _EndOfFunc;
	}

	//Allocating enough memory for the output buffer, cbPlainText:
	pbPlainText = (PBYTE)HeapAlloc(GetProcessHeap(), 0, cbPlainText);
	if (pbPlainText == NULL) {
		bSTATE = FALSE; goto _EndOfFunc;
	}

	//Running BCryptDecrypt again with pbPlainText as the output buffer
	STATUS = BCryptDecrypt(hKeyHandle, (PUCHAR)pAes->pCipherText, (ULONG)pAes->dwCipherSize, NULL, pAes->pIv, IVSIZE, pbPlainText, cbPlainText, &cbResult, BCRYPT_BLOCK_PADDING);
	if (!NT_SUCCESS(STATUS)) {
		printf("[!] BCryptDecrypt[2] Failed with Error: 0x%0.8X\n", STATUS);
		bSTATE = FALSE; goto _EndOfFunc;
	}

_EndOfFunc:
	if (hKeyHandle)
		BCryptDestroyKey(hKeyHandle);
	if (hAlgorithm)
		BCryptCloseAlgorithmProvider(hAlgorithm, 0);
	if (pbKeyObject)
		HeapFree(GetProcessHeap(), 0, pbKeyObject);
	if (pbPlainText != NULL && bSTATE) {
		pAes->pPlainText = pbPlainText;
		pAes->dwPlainSize = cbPlainText;
	}
	return bSTATE;
}

BOOL SimpleDecryption(_In_ PVOID pCipherTextData, _In_ DWORD sCipherTextSize, _In_ PBYTE pKey, _In_ PBYTE pIv,
	_Out_ PVOID* pPlainTextData, OUT DWORD* sPlainTextSize) {

	// FIXED: sCipherTextSize is DWORD, not pointer
	if (pCipherTextData == NULL || sCipherTextSize == 0 || pKey == NULL || pIv == NULL)
		return FALSE;

	AES DAes = { 0 };
	DAes.pKey = pKey;
	DAes.pIv = pIv;
	DAes.pCipherText = (PBYTE)pCipherTextData;
	DAes.dwCipherSize = sCipherTextSize;

	if (!InstallAesDecryption(&DAes)) {
		return FALSE;
	}

	*pPlainTextData = DAes.pPlainText;
	*sPlainTextSize = DAes.dwPlainSize;
	return TRUE;

}

Security solutions can detect the use of cryptographic functions by scanning the IAT, which can potentially indicate malicious behaviour or raise suspicion. Hiding WinAPIs in the IAT is possible.

#### AES Using Tiny-AES Library

This section makes use of the [tiny-AES-c](https://github.com/kokke/tiny-AES-c) third-party encryption library tha performs AES encryption without the use of WinAPIs. Tiny-AES-C is a small portable library that can perform AES128/192/256 in C.

**Setting Up Tiny-AES**

To begin using Tiny-AES there are two requirements:

1. Include `aes.hpp` (C++) or include `aes.h` (C) in the project.
2. Add the `aes.c` file to the project.

**Setting The AES256 Flag**

By default the library applies the AES128 algorithm. One can enable others by enabling one of [AESXXX flags](https://github.com/kokke/tiny-AES-c/blob/master/aes.h#L27) located in the `aes.h` and commenting the other flags accordingly.

eg: for AES256, aes.h would look like:

```c
//#define AES128 1
//#define AES192 1
#define AES256 1
```

**Drawbacks:**

1. Does not support padding. All buffers must be multiples of 16 bytes.
2. The [arrays](https://github.com/kokke/tiny-AES-c/blob/master/aes.c#L79) used in the library can be signatured by security solutions to detect the use of Tiny-AES. These arrays are used to apply AES algorithm and hence is a requirement to have in the code. Though it is possible to modify their signature using different ways. One solution is to XOR these arrays and decrypt them at runtime right before calling the initialisation function, `AES_init_ctx_iv` .

**Custom Padding Function:**

The lack of padding support can be solved by creating a custom padding function.

```c
BOOL PaddBuffer(_In_ PBYTE InputBuffer, _In_ SIZE_T InputBufferSize, _Out_ PBYTE* OutputPaddedBuffer, _Out_ SIZE_T* OutputPaddedSize) {
	PBYTE PaddedBuffer = NULL;
	SIZE_T PaddedSize = NULL;

	//calculate the nearest number that is multiple of 16 and saving it to PaddedSize
	PaddedSize = InputBufferSize + 16 - (InputBufferSize % 16);
	//allocating buffer of size "PaddedSize"
	PaddedBuffer = (PBYTE)HeapAlloc(GetProcessHeap, 0, PaddedSize);
	if (!PaddedBuffer) {
		return FALSE;
	}
	//cleaning the allocated buffer
	ZeroMemory(PaddedBuffer, PaddedSize);

	//copying the old buffer to the new padded buffer
	memcpy(PaddedBuffer, InputBuffer, InputBufferSize);

	//saving result:
	*OutputPaddedBuffer = PaddedBuffer;
	*OutputPaddedSize = PaddedSize;

}
